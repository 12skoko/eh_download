# 特殊模块架构解耦与重构计划

- 日期：2026-09-13
- 状态：已按用户 2026-09-13 的授权完成实现；运行库正式升级仍按第 13 节维护窗口执行
- 范围：特殊处理框架、现有视频模块迁移、LANraragi 数据库核对模块接入
- 现有设计参考：[特殊处理计划](SPECIAL_PROCESSING_PLAN.md)

## 1. 背景与目标

现有特殊处理机制已经具备工作流、任务、租约、后台 worker 和独立页面，但实际执行仍围绕单个 Manga 建立。计划新增的 LANraragi 数据库核对模块需要读取整个数据库与远端档案集合，不应绑定虚构的 Manga，也不应改变 Manga 状态。

本次目标不是仅将 `manga_id` 改为可空，而是建立稳定的模块扩展边界：框架管理工作流执行，模块管理自己的业务对象、操作规则和结果。

完成重构后，新增常规模块应只涉及：

1. 新增模块目录和实现。
2. 增加模块注册声明、配置及必要的展示资源。
3. 按真实业务需要增加模块专用数据表和迁移。
4. 增加模块测试及使用文档。

新增模块不应要求修改通用 worker、任务领取逻辑、Supervisor 调度算法或工作流核心表，也不应在核心增加模块名称、业务阶段或操作名称的条件分支。

本架构覆盖独立任务、单对象任务、多对象任务、人工交互、延迟检查和完成后的维护操作。不承诺任意未来需求都无需扩展框架；新增能力应通过明确契约扩展，不能通过业务特例渗入核心。

### 1.1 一次交付最终架构

本次直接实现上述最终架构，并在同一次交付中完成视频迁移、核对接入、数据迁移和回归验证。禁止先上线可空 `manga_id` 方案、核对专用任务系统或其他临时实现，再安排未来重构。

开发可以按依赖顺序开展，但这些是同一次交付内部的工作项，不是不同架构版本或分批上线方案。正式切换后只运行一套最终模型与执行路径，不保留新旧模型双写、双执行器或“以后再删除”的核心兼容层。

现有视频 URL、CLI 命令和按钮语义作为最终支持的用户接口保留；它们直接调用新模块服务，不以旧框架继续运行来维持兼容。迁移脚本为转换历史数据所需的临时表或字段只能存在于停机迁移过程中，迁移完成前必须清理。

模块注册、配置、关联、并发与互斥、人工与延迟触发、重试与取消、事务与副作用恢复、历史与输出、Web/CLI 扩展、模块数据版本均属于本次交付的完整契约，不留到下一个模块出现时再补架构。

## 3. 架构分层

### 3.1 工作流核心

负责：

- 模块注册与契约校验。
- 工作流创建、操作分发和生命周期管理。
- 任务排队、领取、租约续期、尝试记录及过期恢复。
- 并发额度、资源互斥、取消请求、重试策略。
- 通用事件、进度、输出引用和历史查询。
- 统一事务边界、执行凭据检查与结果提交。

核心不能依赖 Manga 模型、视频操作常量、LANraragi 对比规则或任何模块专用阶段。

### 3.2 可复用集成组件

负责跨模块可复用的业务接入，例如：

- Manga 关联、入口状态校验、普通任务冲突检查。
- Manga 行版本与产物版本保护、状态转换、remark 同步。
- 报告输出与受控下载。
- 现有 LANraragi API gateway 等外部服务能力。

集成组件可依赖对应领域模型；核心仅依赖其契约。本次提供完整的集成扩展边界及 Manga 集成实现，具体外部系统的业务实现随对应模块提供，不建立覆盖所有外部系统的通用适配平台。

### 3.3 业务模块

负责输入、关联对象、业务阶段、操作执行、完成条件、业务补偿和结果展示。

视频与核对模块地位相同，都通过注册契约接入核心。

建议目录结构如下；名称可在实现时按仓库惯例微调，依赖方向不得改变：

```text
special/
  core/
    contracts.py
    registry.py
    repository.py
    service.py
    execution.py
    scheduling.py
  integrations/
    manga/
  modules/
    video_archive/
    lanraragi_compare/
  worker.py
```

模块模板和静态资源可继续保存在现有 Web 资源目录，由模块注册引用，无需为追求目录统一重复实现模板加载系统。

## 4. 持久化设计

本节确定数据库变更范围：**只新增一张 `special_workflow_manga` 表，修改 `special_workflow` 的字段及索引，在现有 `event_log` 上增加查询索引；`special_job`、`manga`、`job_attempt` 不改表结构。** 不新建任务表、资源占用表、特殊事件表或输出表。该选择替代前期讨论中的多表方案，是本次直接交付的最终设计。

| 表 | 确定的变更 |
| --- | --- |
| `special_workflow` | 删除 `manga_id`、`resume_status` 及 `uq_special_workflow_active_manga`；新增非空正整数 `schema_version`、可空时间 `cancel_requested_at`、非空 JSONB `resource_claims`（默认空数组）；为资源查找增加 GIN 索引；保留其他已有字段和索引 |
| `special_workflow_manga` | 唯一新增表；字段为 `workflow_id`、`manga_id`、可空 `resume_status`、非空 JSONB `context`（默认空对象）；前两列组成联合主键，分别通过 RESTRICT 外键引用 workflow 与 Manga；增加以 `manga_id` 为首列的查询索引 |
| `event_log` | 不新增字段；复用 `detail.workflow_id`、`detail.job_id`，增加特殊处理事件的 workflow/job 表达式查询索引 |
| `special_job` | 不新增表、不改字段或约束，复用现有状态、租约、进度、排队时间、尝试次数及唯一索引 |
| `manga`、`job_attempt` | 不修改表结构 |

`schema_version` 由模块显式提供并校验大于零；历史视频数据迁移到本次确定的版本。`resource_claims` 由核心独占维护，内容为资源键、占用范围，以及 job 范围下的 job ID 和执行凭据；按资源键排序并去重。它不是模块任意可写的业务 JSON。

### 4.1 工作流与任务

保留 `special_workflow` 和 `special_job`，避免建立核对模块专用的第二套任务系统。

`special_workflow` 最终承载：

- 模块 `kind` 与模块数据 `schema_version`。
- 生命周期 `status` 与模块自定义 `phase`。
- 经过校验的输入、模块运行数据、结果摘要与进度。
- 行版本、创建者、时间、错误摘要和取消请求信息。

最终模型保留 `payload` 作为模块数据容器，规范输入、业务状态和结果的命名空间及更新接口，避免多个执行路径任意覆盖整份 JSON。不得把核心调度字段藏进模块 payload。

`special_job` 继续承载操作名、尝试次数、触发来源、排队时间、执行状态、租约、错误及时间。通用领取凭据只包含 job/workflow 身份、模块、操作、租约标识与必要的并发版本信息。

核心工作流最终移除 `manga_id`、`resume_status` 等档案专用字段，核心领取凭据移除 `artifact_generation`。

### 4.2 Manga 关联

新增唯一的集成层关联表 `special_workflow_manga`：

- 通过真实外键关联 workflow 与 Manga。
- 保证同一 workflow 与 Manga 关联不重复。
- 支持一个 workflow 关联零个、一个或多个 Manga。
- 保存或引用档案恢复信息、入口快照、预期版本等集成数据。
- 为按 Manga 查询工作流建立索引。

原 `resume_status` 搬到关联行；档案入口快照与预期版本统一放在关联行 `context`，不再为这些小规模业务元数据增加表。保留现有视频业务 payload 的其他信息，不为搬迁而重复保存同一份保护状态。

视频模块要求恰好一个有效 Manga；核对模块不创建关联。

关联表示业务关系，不自动代表独占锁。活动互斥由资源占用机制保证。

不预设决定执行分支的 `manga/global/batch` 核心枚举，也不以无外键的万能对象 ID 替代当前 Manga 的引用完整性。其他对象关系由对应集成组件或模块专用表承担。

### 4.3 事件和输出

事件确定复用现有 `event_log`。当前特殊事件已经在 `detail` 中保存 workflow ID，新的写入契约统一要求数字类型 `detail.workflow_id`，任务事件同时保存数字类型 `detail.job_id`。保留现有操作者、时间、错误和事件类型字段，Manga 关联继续为可选信息。

历史查询直接使用 `component = special_processing` 及 detail 中的 workflow/job 标识，通过对应表达式索引分页查询，不再先按 Manga 取最近 500 条后在内存筛选。索引使用 JSON 表达式值，避免直接将未经核验的旧字符串强制转换成整数。迁移核验旧 ID 的类型与引用，能可靠还原的统一规范化，不能还原的保留原事件且记录异常，不伪造关联。该方案保持现有 JSON 事件关联方式，不新增事件外键或事件表。

输出确定使用 `special_workflow.payload.outputs` 保存小型清单，每项包括稳定输出 ID、来源 job ID、名称、媒体类型、大小、受控存储引用及生成时间；不新增输出表。大型报告内容写入独立运行目录并原子发布，不直接塞进 workflow payload。输出清单由统一接口校验和更新，模块不得绕过租约随意追加。

该清单用于每次工作流的少量报告或产物引用，不存放逐条对比结果或海量文件索引。大型结果由模块在报告文件或其业务存储中分页读取，通过现有输出契约提供入口，不需要调整核心表。

文件系统与数据库无法组成同一事务，应使用稳定输出标识、可重入发布和孤立文件识别策略。只有输出发布成功且结果提交完成，页面才将其展示为有效结果。文件丢失应明确显示不可用，不能伪装为空报告。

### 4.4 模块数据演进

模块声明可读取的数据版本及迁移路径。升级时对不兼容的历史工作流明确暂停执行并给出原因，不得直接按新结构解释旧 payload。

禁用或卸载模块后，通用历史、错误、任务和输出列表仍可查看；缺少执行器时不领取该模块任务。业务专用视图不可用时回退到通用详情。

### 4.5 修改后的 `special_workflow` 完整字段

下面是最终 PostgreSQL 表结构，共 16 个字段，不是只列增量。`TIMESTAMPTZ` 对应 SQLAlchemy 的 `DateTime(timezone=True)`。表中的“程序默认”由 ORM/服务写入，不代表数据库存在 DEFAULT 或自动更新时间触发器；已有字段保持现有默认机制。

| 字段 | PostgreSQL 类型 | 可空 | 默认或写入方式 | 用途 / 变化 |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT` | 否 | 保留现有自增序列 | 主键，保留历史 ID |
| `kind` | `VARCHAR(64)` | 否 | 创建时必填 | 模块 ID，保留 |
| `schema_version` | `INTEGER` | 否 | 模块显式传入，无数据库默认 | 新增，模块数据格式版本 |
| `status` | `VARCHAR(16)` | 否 | 程序默认 `active` | 生命周期，保留 |
| `phase` | `VARCHAR(64)` | 否 | 模块提供初始阶段 | 业务阶段，保留 |
| `payload` | `JSONB` | 否 | 程序默认 `{}` | 模块输入、业务数据、结果摘要、输出清单，保留 |
| `progress` | `JSONB` | 否 | 程序默认 `{}` | 最近进度快照，保留 |
| `row_version` | `BIGINT` | 否 | 程序默认 `0` | 并发版本，保留 |
| `cancel_requested_at` | `TIMESTAMPTZ` | 是 | 未请求时 `NULL` | 新增，核心取消请求标记及记录时间 |
| `resource_claims` | `JSONB` | 否 | 数据库 DEFAULT `'[]'::jsonb`，程序默认空数组 | 新增，核心维护的持久化资源占用 |
| `error_code` | `TEXT` | 是 | `NULL` | 最近错误代码，保留 |
| `error_detail` | `TEXT` | 是 | `NULL` | 最近错误摘要，保留 |
| `created_by` | `TEXT` | 否 | 创建时必填 | 操作者，保留 |
| `created_at` | `TIMESTAMPTZ` | 否 | 程序写入 UTC 当前时间 | 创建时间，保留 |
| `updated_at` | `TIMESTAMPTZ` | 否 | 程序创建及更新时写入 UTC 时间 | 更新时间，保留，不增加数据库触发器 |
| `completed_at` | `TIMESTAMPTZ` | 是 | `NULL`，完成时按现有语义写入 | 完成时间，保留 |

删除的两个字段不再出现在最终表中：

| 旧字段 | 原类型 | 数据迁移目标 |
| --- | --- | --- |
| `manga_id` | `VARCHAR(100) NOT NULL` | `special_workflow_manga.manga_id` |
| `resume_status` | `VARCHAR(32) NOT NULL` | `special_workflow_manga.resume_status` |

最终约束与索引：

| 名称 | 定义 | 变化 |
| --- | --- | --- |
| 现有主键 | `PRIMARY KEY (id)` | 保留 |
| `ck_special_workflow_status` | `status IN ('active', 'completed', 'failed', 'cancelled')` | 保留 |
| `ck_special_workflow_row_version` | `row_version >= 0` | 保留 |
| `ck_special_workflow_schema_version` | `schema_version > 0` | 新增 |
| `ck_special_workflow_resource_claims_array` | `jsonb_typeof(resource_claims) = 'array'` | 新增 |
| `ix_special_workflow_status_updated` | B-tree `(status, updated_at)` | 保留 |
| `ix_special_workflow_kind_phase` | B-tree `(kind, status, phase)` | 保留 |
| `ix_special_workflow_resource_claims` | GIN `(resource_claims jsonb_path_ops)`，服务使用 JSONB 包含查询查找资源键 | 新增 |
| `uq_special_workflow_active_manga` | 旧的活动 Manga 唯一索引 | 删除，互斥改由第 8 节统一协议保证 |
| 旧 `manga_id` 外键 | 原来指向 `manga.manga_id` | 随字段移除，迁至新关联表 |

`resource_claims` 内每项的字段协议固定如下，元素内容由核心校验，数组类型由数据库检查：

| JSON 键 | 类型 | 规则 |
| --- | --- | --- |
| `key` | string | 必填，非空资源键；同一数组内唯一 |
| `scope` | string | 必填，`workflow` 或 `job` |
| `job_id` | integer | 仅 `job` 范围必填，必须属于当前 workflow；workflow 范围省略 |
| `lease_token` | string | 仅 `job` 范围必填，与当前领取凭据一致；workflow 范围省略 |

例如活动视频工作流的占用为：

```json
[{"key": "manga:123456/token", "scope": "workflow"}]
```

视频整合结束后释放 workflow 范围占用；人工源清理实际领取时申请 job 范围占用。不同范围的相同资源键仍互斥，不因为范围不同允许两个冲突执行者同时操作。

### 4.6 新增的 `special_workflow_manga` 完整字段

这是本次唯一新增表，共 4 个字段。它属于 Manga 集成组件；核心执行器不读取该表，视频模块通过集成接口使用它。

| 字段 | PostgreSQL 类型 | 可空 | 默认或写入方式 | 用途 |
| --- | --- | --- | --- | --- |
| `workflow_id` | `BIGINT` | 否 | 创建关联时必填，无自增 | 所属工作流 |
| `manga_id` | `VARCHAR(100)` | 否 | 创建关联时必填 | 关联档案 |
| `resume_status` | `VARCHAR(32)` | 是 | 默认 `NULL`；视频模块创建时必须填写原状态 | 模块改变档案状态时的恢复目标；只读关联可为空 |
| `context` | `JSONB` | 否 | 数据库 DEFAULT `'{}'::jsonb`，程序默认空对象 | 档案入口快照和版本保护数据 |

约束与索引：

| 名称 | 定义 |
| --- | --- |
| `pk_special_workflow_manga` | 联合主键 `(workflow_id, manga_id)` |
| `fk_special_workflow_manga_workflow` | `workflow_id → special_workflow.id ON DELETE RESTRICT` |
| `fk_special_workflow_manga_manga` | `manga_id → manga.manga_id ON DELETE RESTRICT` |
| `ck_special_workflow_manga_context_object` | `jsonb_typeof(context) = 'object'` |
| `ix_special_workflow_manga_manga` | B-tree `(manga_id, workflow_id)`，支持档案详情反查工作流 |

不增加独立自增 ID、时间字段或重复的状态列；关联生命周期随工作流管理，变更历史写入已有 event_log。不对 `manga_id` 单列设唯一约束，否则会阻止保存同一档案的历史工作流。

`context` 的 Manga 集成协议如下，不由核心解释：

| JSON 键 | 类型 | 用途 |
| --- | --- | --- |
| `entry` | object | 迁入原视频 payload 中的档案入口信息，如 reason、原错误代码/操作/详情；缺失时为空对象 |
| `expected_manga_version` | integer 或 null | 某次业务操作建立的档案版本基线，由集成组件按现有保护语义设置和更新 |
| `expected_artifact_generation` | integer 或 null | 某次业务操作建立的产物版本基线；null 表示尚未建立，不能据此跳过需要的版本检查 |

该 JSON 不存凭空推测的历史版本，也不在迁移时把当前 Manga 版本伪装成旧任务领取版本。新操作执行前按原规则建立并校验基线，相关提交继续与工作流状态在同一事务内完成。

### 4.7 `event_log` 的具体索引变更

现有 event_log 全部字段、默认值、外键和原有索引保持不变，只新增以下两个部分 B-tree 表达式索引：

| 索引名称 | 索引键 | WHERE 条件 |
| --- | --- | --- |
| `ix_event_special_workflow_created` | `(detail ->> 'workflow_id', created_at DESC, id DESC)` | `component = 'special_processing'` |
| `ix_event_special_job_created` | `(detail ->> 'job_id', created_at DESC, id DESC)` | `component = 'special_processing'` |

查询使用同一文本提取表达式，以规范化 ID 的十进制字符串为条件；不将旧 JSON 强制转整数，不把 detail 转成 JSONB，也不新增事件字段。写入仍保存 JSON 数字，`->>` 仅用于索引和查询。索引 SQL 应在 Alembic 中正确包裹表达式，并在 PostgreSQL 测试中验证查询计划及排序分页行为。

### 4.8 输出清单的结构（不是新增表）

`payload.outputs` 为数组，每项定义如下：

| JSON 键 | 类型 | 用途 |
| --- | --- | --- |
| `id` | string | 工作流内唯一、重试可复用的稳定输出标识 |
| `job_id` | integer | 实际生成本输出的 job ID |
| `name` | string | 用户看到的报告名 |
| `media_type` | string | 如 `application/json` |
| `size_bytes` | integer | 文件字节数，非负 |
| `storage_key` | string | 受控输出根目录下的相对存储键，不接受任意路径 |
| `created_at` | string | UTC ISO 8601 生成时间 |

没有输出时使用空数组；历史视频工作流不凭空生成报告条目，已有最终产物仍按视频原产物登记机制管理。相同输出 ID 的幂等发布由统一接口处理，不重复追加清单。

### 4.9 字段级迁移对照与核验

| 来源 | 最终目标 | 迁移要求 |
| --- | --- | --- |
| 原 workflow 的 `id`、`manga_id`、`resume_status` | 新关联表的对应三列 | 每个旧视频 workflow 生成恰好一条关联，包含已完成、失败和已取消记录；核验后删除旧两列 |
| 原视频 `payload.entry` | 新关联行 `context.entry` | 原值迁入，新模块同步改为从关联读取，不保留两份可变事实 |
| 历史版本保护信息 | `context` 中对应基线 | 只迁入有证据且仍适用的值；缺失为 null，不能重建未知运行中任务的旧凭据 |
| 旧视频模块数据 | `schema_version = 1` | 本次最终视频数据格式定义为版本 1；后续格式变化由模块升级契约管理 |
| 原取消请求 | `cancel_requested_at` | 已取消终态不重新制造请求；未完成请求优先使用可靠事件时间，无时间则以迁移记录时间填入并在事件中注明来源，不能伪称原请求时间 |
| 活动工作流及未解决占用 | `resource_claims` | 按原互斥语义回填；失败但仍需保留对象控制权的工作流不能简单当作空占用，冲突必须阻止切换 |
| 原任务、事件和产物记录 | 原表及原 ID | 保留历史；只规范化有可靠依据的事件关联，原产物不重复登记 |

取消的最终控制来源是 `cancel_requested_at`；旧 payload 的控制标记在本次迁移中清除，模块不再并行读取旧标记。具体旧状态的映射必须覆盖数据库实际存量，不通过默认值吞掉异常。

字段删除前必须验证：旧 workflow 数量与迁入关联数匹配、联合主键无重复、外键无孤立行、恢复状态一致、JSON 结构合法、schema_version 正确、资源占用无冲突。迁移后再检查所有保留 workflow/job ID、视频页面入口和等待中的工作流可用。

已有历史迁移 `0013_special_processing` 提到初始迁移可能根据当前 ORM 元数据建表，因此实现时必须同时验证旧库升级和空库完整迁移两条路径，避免最终模型已无旧字段时迁移仍强行读取旧列。两条路径结束后必须得到本节相同的最终结构，不另建兼容模型。

## 5. 模块契约

每个模块导出统一描述对象，并在一个明确的装配入口注册。启动时校验重复 ID、重复操作、无效阶段引用、配置和数据版本声明。

| 契约 | 必须表达的内容 |
| --- | --- |
| 模块身份 | 稳定 ID、名称、描述、数据版本 |
| 配置与能力 | 配置解析、启用状态、依赖检查、并发上限 |
| 创建契约 | 输入校验、关联要求、初始化业务数据与入口保护 |
| 操作定义 | 输入结构、允许生命周期及阶段、执行器、运行阶段 |
| 执行策略 | 超时、租约、可重试错误、最大尝试次数及退避 |
| 互斥策略 | 资源键、占用范围和释放条件 |
| 交互动作 | 可见条件、可执行条件、所需输入及权限 |
| 展示扩展 | 概览、详情、结果查询和可选专用模板或路由 |

页面可见条件只用于展示；创建、排队和执行前都必须在服务端校验实际前置条件。

框架提供统一执行上下文，包含配置访问、日志、事务入口、进度更新、输出发布和取消检查。上下文不默认携带 Manga；模块通过集成组件读取自己的业务对象。

事务内的业务校验与更新通过明确回调完成，网络请求、转换和文件处理在事务外执行。模块不得自行绕过租约提交工作流终态。

## 6. 生命周期、阶段与执行结果

生命周期沿用 `active/completed/failed/cancelled`；业务阶段由模块定义。job 状态与 workflow 状态独立，不能将一次 job 成功等同于整个工作流完成。

统一操作结果至少表达：

1. 操作成功，进入指定业务阶段。
2. 等待人工动作，不安排后台轮询。
3. 等待外部条件，保存状态并安排未来检查。
4. 工作流完成，保存结果摘要和输出引用。
5. 执行失败，按声明进入重试、可人工恢复或终止状态。

延迟检查通过 `next_run_at` 等持久化队列机制执行，不让 worker 长期 sleep 等待下载或用户。

自动后续操作、延迟检查和自动重试均为模块明确选择的能力，核心默认不替模块推进业务。视频模块保留人工排队策略，不因框架支持这些能力而自动检查下载、重试、整合或清理。

允许操作声明在 `completed` 工作流上执行，以及失败是否影响工作流生命周期。视频源清理是首个实例：清理失败只影响清理结果，不撤销已成功完成的整合。

用户请求重新执行应明确区分：失败 job 的重试、同一工作流的后续操作、以新输入创建新工作流。核对的“重新核对”创建新的 workflow，保留每次采集历史。

## 7. 执行一致性与恢复

### 7.1 租约和版本保护

- 原子领取任务并生成新的执行凭据。
- 长任务使用受控续租；进度与业务数据版本不应因心跳更新而无意义冲突。
- 每次进度、阶段和结果提交都验证当前执行身份。
- 租约过期的旧 worker 不得提交或覆盖新执行结果。
- 领取事务、续租事务和结果事务保持短事务，执行外部操作时不持有数据库长锁。

### 7.2 外部副作用

框架不能保证远端操作恰好执行一次。模块需声明操作属于只读、幂等写入或需要核实恢复的写入，并提供相应恢复逻辑。

上传、下载提交、删除等操作需保存稳定幂等标识或外部执行证据。发生“外部已成功、数据库未提交”时，先核实外部状态；证据不足则进入人工处理，不能盲目重跑。

数据库租约只能阻止旧执行者提交本地结果，不能撤回其已经发出的远端请求。可能仍在执行的旧进程必须纳入恢复判断。

### 7.3 取消与失败

- 取消是持久化请求，由执行器在安全检查点响应。
- 进程终止不等于业务取消成功。
- 是否撤销远端任务、保留产物或清理临时文件，由模块定义。
- 临时错误按声明退避；配置错误、业务冲突和未知副作用不能无限自动重试。
- 恢复失败任务时保留原尝试和事件，不覆写历史。

## 8. 并发与资源占用

并发额度包括系统级和模块级上限，均需独立生效。使用 PostgreSQL 事务级 advisory lock 串行化特殊处理的短调度事务，在同一事务中核对现有 running job 数量、资源占用并完成领取，保证多 Supervisor 不超额；不能仅统计单进程子进程数量。保留存量执行租约和未核实旧进程的保守恢复规则，不能为腾出额度直接启动重复执行。

资源互斥使用稳定的资源键：

- 视频操作使用 `manga:<id>`。
- 全量核对使用按 LANraragi 实例标识划分的核对键，不使用包含凭据的 URL。
- 多对象模块根据业务要求申请多个资源键。

占用必须区分整个活动工作流期间与单次 job 执行期间。已完成工作流的维护操作如需互斥，应重新申请执行期间的占用。

资源占用确定存放于 `special_workflow.resource_claims`，不新增资源表。所有申请、释放、任务领取及占用恢复都通过同一核心仓储入口，在同一个约定的事务级 advisory lock 下执行。先查询所有仍保存有效占用的工作流（包括终态维护任务），再一次性写入整组申请；事务回滚不会留下部分申请。

此处跨工作流的资源唯一性由统一加锁协议保证，不声称 JSON 字段自身具备跨行唯一约束。所有占用写入必须遵守协议，模块不能直接编辑 resource_claims。多资源在一次短事务中核验并原子申请，冲突任务跳过或延迟，不能阻塞其他可执行任务。锁必须先于相关行锁获取，统一锁顺序，防止领取、完成和取消路径相互死锁。

这项选择用短调度事务的串行化换取更少的表，网络访问、下载、转换和报告生成仍在事务外并发执行。需要测试锁竞争与调度延迟，但不以建立第二套资源表作为后续既定步骤。advisory lock 只保护事务中的读改写；跨 job、跨进程重启的占用由持久化 resource_claims 保留，不能只持有进程会话锁来表示业务占用。

工作流级占用不能仅因单个 job 租约到期就自动释放；需先判断工作流及副作用恢复状态。终态、取消及异常恢复的释放规则应有独立验证。

Manga 普通流程不自动参与新资源锁系统，Manga 集成组件仍必须通过原有档案状态、活动任务和租约检查协调普通流程。

## 9. Web、CLI、配置和运维

### 9.1 页面

沿用 `/special` 模块目录及模块独立控制台。通用外壳展示状态、进度、动作、任务历史、日志与输出；模块提供业务内容。

通用动作分发以注册的模块和操作为白名单，统一认证、输入校验、并发版本检查与错误响应。复杂业务页面可注册专用路由，不要求所有界面都压进一种表单。

保留视频现有 URL，必要时通过兼容入口转发到新服务。档案详情通过 Manga 集成组件查询关联工作流。

分页查询与筛选在服务端实现，大型核对报告不得一次全部渲染到 HTML。

### 9.2 CLI 与配置

Web 与 CLI 调用相同命令服务，避免两套创建和重试规则。现有视频命令保持兼容。

核心配置管理全局并发、调度周期和默认租约；模块配置自行管理业务参数及覆盖值。启用状态检查与外部连通性探测分开，打开模块目录不应触发慢网络探测。

继续采用代码中明确注册的模块，不纳入动态上传插件、运行时任意代码加载或热卸载。

### 9.3 运维可见性

日志和事件统一包含 module、workflow、job 与 attempt。页面区分模块禁用、依赖不可用、等待输入、等待外部条件和任务失败。错误输出沿用脱敏规则，不泄漏认证头及密钥。

## 10. 视频模块迁移契约

### 10.1 保持现有人工工作流

本次是执行框架重构，不是视频业务流程改版。采用模块适配方式迁移现有操作，保留按钮语义、操作顺序、触发时机和等待阶段，不额外增加审批或“完成确认”步骤。

现有注册表定义五种后台操作：加载候选 `load_torrent_options`、提交所选种子 `submit_selected_torrents`、检查并整合 `check_and_compose_if_ready`、取消 `cancel_video_archive`、完成后源清理 `cleanup_sources_after_complete`。从档案进入视频处理、选择候选等页面动作与后台操作不是一一对应，不能用后台操作数量推断用户步骤数量。

| 用户阶段 | 迁移后必须保留的触发方式 |
| --- | --- |
| 进入视频处理 | 按原档案状态及入口规则提供入口，由用户启动；状态符合不等于自动启动 |
| 加载与选择种子 | 保留现有候选加载入口，由用户选择图片和视频种子并确认提交 |
| 等待下载 | 不自动创建下载检查任务；页面刷新不触发外部业务检查 |
| 检查并整合 | 用户单个或批量触发；一次任务内按原逻辑检查，满足条件后转换、打包、登记；未就绪则等待下次人工检查 |
| 整合结束 | 由该次整合任务提交完成结果，Manga 按现有契约回到 downloaded，后续普通校验、上传和 cleanup 保持原流程；不增加独立完成按钮 |
| 源文件清理 | 对应 Manga 到达 completed 后，由用户单个或批量触发，不随整合或普通流程完成自动创建 |
| 重试、取消及受控退出 | 保留原有人工入口、可用条件和安全检查，不新增自动重试或自动解除租约策略 |

Supervisor 负责执行已排队任务，不替用户决定视频模块下一步。任务内部连续执行的转换、打包和登记仍维持原行为，不能把每个内部阶段拆成需要点击的新步骤。

### 10.2 业务保护与历史兼容

必须保留：

- 恰好关联一个有效 Manga。
- 原有入口状态、错误条件及人工启动规则。
- 普通任务、租约与活动特殊工作流冲突检查。
- 原有 Torrent 选择、下载、转换、打包及登记行为。
- Manga 行版本、产物 generation 和过期执行检查。
- 完成、失败、取消与强制退出时的状态恢复规则。
- remark、错误记录及事件同步。
- 完成后源清理的人工入口，以及 hash、category、保存路径校验。
- 产物已发布而登记事务失败后的可恢复行为。

上述业务规则迁入视频模块及 Manga 集成组件；通用核心不保留视频操作特判。

现有 `ready` 工作流和完成后清理任务的生命周期组合应逐一映射，不通过批量改成 active 简化迁移。

## 11. LANraragi 核对模块作为扩展性验收

标识建议为 `lanraragi_compare`。手动启动，使用通用 workflow/job 执行：

`排队 → 读取 LANraragi → 读取数据库 → 比较 → 发布报告 → 完成`

首版沿用 `scripts/compare_lanraragi_database.py` 的基础口径：数据库 completed 集合与 LANraragi 标签提取的数字 GID 比较。共用解析与比较逻辑应移入主程序，脚本保持兼容入口。

报告包含双方独有、重复 GID、数据库无效 ID、LANraragi 无法解析档案。对 LANraragi 独有项可补查数据库其他状态，但不改变原始统计口径。

记录两端采集时间；GID 匹配不代表文件内容一致，双方采集也不是跨系统原子快照。接口失败或结构错误必须使本次任务失败，不能解释为空库。

核对不修改 Manga 状态，不创建 Manga 关联，使用按实例划分的互斥键，结果作为通用输出保存。本次业务范围不包含自动修复、删除或补采，这不是框架能力分期建设的理由。

接入本模块时若仍需修改核心调度或新增业务特判，视为解耦验收未通过，应先修正契约。

## 12. 单次交付的工作清单

以下工作项按依赖推进，全部完成并验收后才正式切换，不单独上线中间架构。

### A. 行为基线与最终契约

- 梳理视频所有入口、操作、状态转换及异常恢复路径。
- 对照现有测试补齐关键行为验证。
- 定稿模块契约、数据模型、资源占用和事务边界。
- 盘点现有数据库中各类 workflow/job 组合，制定明确映射。

交付：契约定义、迁移映射和回归验证清单；不同时改动视频算法。

### B. 最终核心与集成组件

- 建立注册、命令分发、执行结果与上下文。
- 拆出 Manga 集成逻辑。
- 通用领取查询解除 Manga join，通用失败处理解除档案写入。
- 统一操作策略、并发、互斥、事件和输出接口。

交付：能执行无 Manga 工作流的核心及必要的迁移脚本。

### C. 视频业务等价迁移

- 视频完整接入新契约。
- 保持现有 Web/CLI 入口与工作流 ID。
- 验证在等待选择、下载、失败和已完成阶段的历史工作流可继续操作。
- 清除核心中视频常量、模块名称判断及业务阶段特判。

交付：功能兼容的视频模块及通过的回归验证。

### D. 核对模块与扩展性验证

- 抽取共用比较逻辑，保留脚本接口。
- 新增模块配置、执行器、控制台和报告浏览。
- 验证新增模块不需要修改核心架构。

## 13. 数据迁移与部署方案

采用维护窗口内一次转换到最终结构、整套程序一次切换的部署方式。正式部署前在可恢复的数据库副本上完成全量迁移演练和回归验证。迁移脚本必须随代码版本管理，不能依靠人工直接编辑运行库。

1. 暂停新任务领取，等待正在执行的 job 结束；工作流等待用户或下载可保持持久化等待状态。
2. 停止相关程序写入数据库，备份并核验恢复方式，记录 workflow/job 数量与关键状态分布。
3. 在同一维护窗口执行完整迁移：建立最终关联和框架字段，回填 Manga 关系、恢复信息、模块数据版本及资源占用。
4. 核验关联、外键、资源冲突、历史任务、已完成清理记录及阶段映射；校验失败时禁止启动新版本。
5. 在迁移结束前移除旧核心字段及迁移临时结构，确认数据库已经处于最终模型。可事务化的迁移原子提交，其余步骤必须具备明确失败恢复措施。
6. 整套切换 Web、CLI、Supervisor 与 worker 到最终版本，不允许新旧执行器混用。
7. 保持调度暂停完成上线检查；确认通过后恢复调度，本次切换即交付最终架构。

回滚边界必须明确：旧程序无法解释无 Manga 工作流和新契约数据。尚未运行新业务时可恢复备份并整套回退程序，不能只切回旧二进制；已执行外部副作用后，不能仅恢复数据库备份，应先核实外部状态并制定恢复措施。备份和迁移演练是部署恢复手段，不是保留中间架构的理由。

## 14. 测试与验收

测试统一放在 `tests/`。执行 Python、pytest 或其他项目环境命令前先 `conda activate eh`，Windows 终端使用 PowerShell 7。

### 14.1 核心验证

- 无 Manga 的工作流能够创建、领取、成功、失败、重试和取消。
- 人工等待和延迟检查不占用长期 worker。
- 重复动作不产生重复活动 job。
- 多执行者竞争时领取、并发额度和资源互斥正确。
- 租约过期与旧 worker 晚提交不覆盖新状态。
- 资源冲突不阻塞其他可运行任务。
- 多 Supervisor 在统一事务锁下竞争额度及多个资源键时无重复占用，失败事务无部分占用，重启后占用仍存在；完成、取消、维护操作遵守同一锁顺序。
- 已完成工作流的维护操作失败不改变其主结果。
- 模块禁用、未注册、配置异常和数据版本不兼容均有明确行为。

涉及 PostgreSQL 锁、部分唯一索引和并发的验证应在 PostgreSQL 上完成，不能只依赖 SQLite 测试结果。

### 14.2 视频回归

- 无用户动作时不创建检查、整合、源清理或失败重试任务；普通页面刷新不推进视频业务。
- 单个与批量按钮保持原语义；检查未就绪后继续等待人工操作。
- 整合任务成功后按原契约返回普通流程，不增加完成确认；普通流程结束不自动触发特殊源清理。
- 新建与现有工作流继续运行。
- 候选加载、选择提交、检查、整合与登记。
- 状态冲突、产物版本变化及租约失效保护。
- 重试、取消、强制退出与错误恢复。
- 完成后人工清理，以及错误 hash/category/path 的拒绝行为。
- 产物已发布、数据库提交失败等中断恢复场景。

### 14.3 核对验证

- 同一输入下与旧脚本基础统计一致。
- 重复、无效、缺失来源及其他数据库状态的正确展示。
- 网络错误、鉴权失败、非法 JSON 和空结果的区分。
- 重复启动、报告发布中断、文件缺失及重新核对历史保留。
- 核对过程不写入 Manga 业务状态。

### 14.4 架构验收

- 数据库变更严格遵守第 4 节：仅新增 `special_workflow_manga`，修改工作流字段及索引，补充现有事件查询索引；不建立独立任务、资源、事件或输出表。
- 一次性交付最终数据模型和执行路径，无可空 Manga 临时方案、核对独立队列、双写或留待以后拆除的核心兼容层。
- 使用契约级测试模块验证无关联、多对象关联、人工等待、延迟检查、终态维护和专用展示扩展，避免仅凭两个实际模块运行成功就认定所有扩展边界完整。
- 普通模块的调度资格、并发额度、暂停恢复、错误退避和子进程回收行为与重构前一致；特殊任务故障不得无依据扩大为普通模块暂停，原有全局故障规则保持原义。
- 核心无 Manga 模型依赖和视频业务常量依赖。
- Supervisor 无按业务模块分支的调度代码。
- 核对模块使用与视频一致的任务、租约、历史和输出机制。
- 新模块仅增加实现、注册、配置、展示资源及必要专用表。
- 文档明确如何新增模块、声明副作用和处理历史数据版本。

## 15. 范围边界与完成定义

本次不建设通用 DAG 编排器、任意脚本执行平台、动态插件市场、跨机器分布式执行系统或自动对账修复系统。多对象关联不自动承诺大型批处理能力；需要逐项检查点、部分失败和海量数据时，由业务模块基于专用表实现，继续使用核心调度契约。

完成条件是：视频模块完成兼容迁移，核对模块在不增加核心业务分支的情况下接入，历史数据可继续操作，关键一致性与恢复验证通过，过渡耦合已清除，使用及扩展文档齐全。

以视频模块证明业务兼容，以核对模块证明架构解耦。
