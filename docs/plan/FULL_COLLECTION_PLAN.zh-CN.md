# 全量采集、手动补齐与断点续跑实施计划

日期：2026-09-28  
状态：方案修订，尚未实施。本文修改仅限计划文档，不代表程序修改授权。

## 1. 本轮确认的范围

在现有 collect 的基础上增加全量采集模块，复用列表解析和数据库，不建立独立目录系统。

- 不新增数据库表、字段或状态枚举。
- 新档案写入 manga，status = filtered_out，remark 添加固定全量建档标记。
- 已有档案只更新采集元数据，不修改状态、备注或其他业务字段。
- 历史回填首次从一周前的边界开始，可使用站点日期定位、数据库旧记录定位或手工分页 URL；不默认从最新页开始。
- 补齐轮次只能由用户手动创建，不定时补齐，不因启动、重启或历史完成而自动创建。
- 每页提交并保存断点，支持暂停、继续，以及调度器重启后的恢复。
- 全量使用独立账号与代理池，按小时轮换，适合重试的请求错误触发换代理。
- 模块详情页属于本期范围，提供进度、错误、代理状态及运行控制。
- screen 新增独立的必需标签门槛，为未来无筛选网址的普通增量采集做准备。
- 新增专用 full_collect.toml 配置文件；筛选规则和秘密信息仍放在各自现有配置中。

本期不包含全站图片下载、历史并行分片、全站详情页主动补全、全量 filtered_out 自动重新送筛、自动周期补齐。

## 2. 当前代码与需要纠正的旧行为

| 位置 | 已检查的行为 | 实施方向 |
| --- | --- | --- |
| tasks/collect.py | 多个来源全部翻页在同一事务中 | 全量单独入口，每页短事务 |
| services/collector/service.py | 翻页与写库耦合，累计所有结果 | 提取单页接口，复用解析；全量不累计长期明细 |
| db/repository.py | upsert_manga 会重新分类已有 deferred | 增加元数据专用更新路径，禁止全量触发状态转换 |
| services/screening/policy.py | tag_keywords 命中可直接 QUEUE | 新增必需标签前置门槛，不能复用该字段 |
| integrations/http.py | 固定代理、账号选择、间隔和重试已有；无代理池选择 | 增加全量角色与可选轮换策略 |
| old/collect_full.py | 当前小时加错误偏移选择代理，每页等待 10～30 秒 | 复用机制，修正超时与错误处理 |
| supervisor 与模块网页 | 已有模块状态、触发、暂停和调度器停止机制 | 扩展为全量长任务控制，不能只停止下一次调度 |

旧全量脚本实际使用 cookies_with_donation，旧普通采集使用 cookies_non_donation；新版明确配置全量账号，不直接照搬旧变量。

旧全量脚本在当前页入库前就写下一页编号，存在漏页风险。新版必须先提交数据库，再保存下一页断点。

## 3. 数据库与记录更新

### 3.1 是否迁移数据库

**不需要数据库结构迁移，不新增表、字段、索引或业务状态。**

- 档案复用 manga 表。
- 模块启停请求、暂停和运行意图可复用现有 SystemControl 等控制设施，增加模块对应的记录不等于增加表。
- 采集边界、轮次、统计、运行快照保存为持久 JSON 文件。
- 现有日志设施记录模块操作与错误摘要，不为每次重复采集制造状态变化事件。
- 实现前核对现有控制字段语义，不能把档案状态和模块状态混用；若现有字段不够，用受控状态文件，不暗中增加 schema。

### 3.2 新档案

- 使用原有 manga_id 唯一键。
- status = filtered_out。
- remark = 固定标记，例如 `[full_collect] 全量收集建档`。
- queue_source 使用现有合法值 automatic。
- 写入正常列表元数据，不应用普通观察期，不进入 discovered 或 deferred。

### 3.3 已有档案：元数据白名单

允许更新：name、real_name、link、torrent_link、posted_at、category、tags_raw、pages、rating、uploader、source_fetched_at。通用 updated_at 可按现有约定反映此次元数据更新。

禁止更新：status、status_updated_at、remark、queue_source、defer_until、screen_group_id、priority、下载上传字段、人工控制字段、租约、错误状态、尝试记录及其他业务控制字段。不调用状态转换方法，不清空缺省业务字段，不整体覆盖 ORM 记录。

即使已有记录是 deferred、discovered、downloading、completed 或 filtered_out，也遵循同一规则。不能因为全量刷新了标签就顺便启动筛选、重置进度或追加备注。

已有条目不是翻页结束条件。保留唯一键和少量并发插入冲突重试即可，不设计复杂的跨采集协调系统。

## 4. screen 必需标签规则

### 4.1 背景与顺序

当前普通 collect 的网址已限定某个标签，screen 因而没有重复检查这个条件。未来普通增量入口改成无标签筛选网址时，必须把该条件显式移入 screen。

新增 `screen_required_tags`，与现有 `collect_tags`、`tag_keywords` 分开：

- collect_tags：构造采集网址。
- tag_keywords：现有筛选中命中后直接选入的关键词。
- screen_required_tags：是否有资格继续参加筛选的前置门槛。

顺序为：读取 EH discovered 候选 → 必需标签检查 → 现有排除、关键词及版本筛选。缺少必需标签时转为 filtered_out，并记录明确的筛选原因；不得被名称关键词或 tag_keywords 的直接选入分支绕过。界面可显示“缺少必需标签”，日志原因可用 required_tag_missing。

标签按 namespace:name 规范化后精确匹配，不能用容易误中的任意子串匹配。处理大小写、首尾空格及当前 tags_raw 的实际存储格式。多标签支持 all/any；单标签两者等价。空列表保持旧行为。

同名分组筛选也要使用相同准入规则：不符合门槛的待筛选候选不能参与版本竞争或反过来淘汰合格候选。已进入下载、已完成等记录仍按现有业务规则处理，不因这次规则上线回退状态。其他来源如 PicACG 不因 EH 标签规则被误伤。

具体必需标签尚未给出，实施前从用户确认的现有采集条件中确定；不能猜测成某个标签，也不能把任意搜索表达式自动转换为精确标签。

### 4.2 与全量 filtered_out 的关系

本期继续保持全量新记录为 filtered_out；新增门槛不代表自动扫描这些历史记录。

该门槛服务于现有 discovered 候选，以及未来无筛选普通增量产生的 discovered。将全量历史档案批量重新送筛属于独立功能，本期不隐式执行。只刷新已有 filtered_out 的元数据也不改变其状态。

## 5. 历史首次起点

### 5.1 三种起点方式

| 模式 | 行为 |
| --- | --- |
| 日期定位（默认） | 初始化时冻结“当前时间减 7 天”的目标时间，使用站点支持并已验证的日期/游标定位方式 |
| 数据库定位 | 查找目标时间附近、不晚于目标时间的 EH 记录，以其数值 GID/链接辅助定位同一站点的列表页 |
| 手工 URL | 用户给定实际可访问的无业务筛选分页 URL；解析和验证后作为首个候选页 |

数据库不存在“一周前的一页”这个历史页面对象。数据库模式只是用记录定位，不能直接把该记录当成一整页已覆盖的证明。没有合适记录时明确报告或由用户选择日期/URL，不静默回退最新页。

日期定位和数据库定位的分页语义必须用真实页面样本验证，不猜测 next 参数包含/排除边界的含义。相同时间多条记录、边界记录删除及站点排序变化都应有测试。

### 5.2 安全边界

- 首次目标时间和解析出的真实页边界持久化，重启不重新计算“今天减 7 天”。
- 允许为了定位读取边界附近页面，但不将目标时间之后的近期记录当作本轮历史范围写入。
- 分页可能跨越目标日期，要逐条应用本轮范围检查，并保留足够的页边界信息，避免漏掉目标时间附近条目。
- URL 需要固定站点、列表模式及无业务筛选范围；账号默认过滤的影响应在初始化检查中提示。
- 普通 collect 的实际覆盖范围不是固定七天，因此“一周前”是减少重叠的起点选择，不作为绝不重叠的证明；已有记录元数据更新规则仍必须可靠。

## 6. 手动补齐轮次

### 6.1 创建与范围

取消旧计划中的每日补齐、到期检查、自动切换与历史完成后的定时补齐。

用户在详情页或 CLI 点击/执行“新建补齐轮次”，先展示范围，再启动：

- 新边界默认定位到本次操作时的一周前，允许用户显式指定日期或分页 URL。
- 旧边界使用最近已覆盖的上边界；第一次使用历史初始化的已落库边界。
- 从新边界向旧边界逐页扫描，并完成有限交界重叠检查。
- 补齐页同样新增 filtered_out、已有仅刷新元数据。
- 本轮完成后更新已覆盖上边界，不自动创建下一轮。

示例：9 月 27 日首次历史回填从约 9 月 20 日开始。11 月 1 日手动补齐，默认新边界约为 10 月 25 日，本轮补齐约 9 月 20 日至 10 月 25 日的区间。10 月 25 日之后的无筛选全量数据仍待用户后续补齐；普通 collect 只覆盖其原筛选范围，不能把这段标成全量完整。

边界仍使用真实分页锚点和经过验证的比较规则，日期仅用于用户选择和显示。不能仅遇到一个已存在 ID 就认定补齐完成。

### 6.2 与历史任务的关系

- 同时只运行一个全量工作进程，不并行跑历史和补齐。
- 创建补齐轮次前，先在页边界暂停历史任务，保存历史位置。
- 补齐完成后进入空闲；由用户点击“继续历史”，不自动切回。
- 尚有未完成补齐轮次时只能继续该轮，不能静默覆盖边界或新建另一轮。
- 补齐中断保留本轮起点、目标旧边界、下一页位置和完成状态。
- 调度器重启可以恢复已经手动创建且处于运行意图的轮次，但这不等于自动创建补齐。
- 历史完成但存在尚未手动补齐区间时，界面分别显示，不能宣称全站已全部完成。

## 7. 逐页事务与文件状态

### 7.1 提交顺序

请求和解析页面 → 校验条目与分页 → 短事务写入当前页 → 提交数据库 → 原子保存 JSON 断点 → 处理下一页。

数据库提交和文件保存不能形成统一事务，因此允许重放当前页、不允许跳过未提交页。数据库提交成功但文件保存失败时停止推进，下次重放。当前页部分条目解析失败不能悄悄跳过并推进断点；错误页面不能当作末页。

JSON 使用同目录临时文件、刷新和原子替换。只保留当前页明细和有界统计，避免持续增长的内存。

### 7.2 状态文件内容与责任

- 格式版本、站点与影响结果的配置指纹。
- 历史目标时间、初始边界、下一页 URL、最近成功页范围、完成状态。
- 已覆盖上边界、当前手动补齐轮次 ID、固定新旧边界、下一页 URL、轮次状态。
- 每种任务的提交页数、处理条目数、新增与更新数、最近成功时间。
- 当前任务方向、运行 ID、心跳、错误摘要、冷却截止时间和最近停止原因。

详细进度文件由工作进程单写。Web/Supervisor 的暂停和继续请求通过现有控制设施发送，不能直接读改写工作进程的整份 JSON，避免覆盖检查点。工作进程退出后需要初始化/创建轮次时，启动器必须先取得同一文件锁再写。

同一断点使用操作系统进程锁，进程退出可释放；限定同主机持久目录，不依赖锁文件是否存在。Web 与 Supervisor 必须指向同一状态路径；不同机器部署不靠复制快照实现控制。

状态文件损坏或不兼容时明确停止，不自动清空。进度是续跑依据，日志只是诊断。文件迁移和备份必须纳入部署说明，不能放在会轮转删除的日志目录。

## 8. 长任务控制与调度器重启

### 8.1 接入方式

将 full_collect 作为可见、可控制的模块接入现有模块列表、详情页与 Supervisor，但使用手动长任务语义，不套用普通 interval/condition 周期自动启动方式。模块启用不等于开始抓取。

现有模块暂停主要影响后续启动，全量工作进程必须额外轮询暂停/停止请求；现有 drain 等待子进程退出的行为也要扩展，否则长期任务会一直阻挡调度器重启。

### 8.2 控制行为

| 操作或事件 | 预期结果 |
| --- | --- |
| 开始历史 | 用户显式启动，解析起点，开始回填 |
| 暂停 | 立即显示“正在暂停”；完成或放弃当前未提交页，保存最后成功断点，退出子进程 |
| 继续 | 恢复同一任务与冻结边界，不重新初始化 |
| 手动补齐 | 历史先暂停，创建用户选定的单个轮次 |
| 补齐完成 | 空闲等待用户操作 |
| 历史完成 | 标记历史完成，不创建补齐 |
| 调度器正常重启/drain | 向全量子进程发出可协作停止请求，限时等待，重启后按配置恢复原任务 |
| 用户主动暂停后重启 | 保持暂停，不能自动拉起 |
| 强制结束或机器掉电 | 检查旧进程存活与锁，恢复最后成功断点，不重复启动 |
| 全量模块失败 | 错误局限于本模块，不触发普通流程全局停止 |

区分“用户暂停”和“运行中的任务因调度器重启而中断”。建议 resume_after_restart 默认 true，但只对已经启动、未被用户暂停且未完成的任务生效；设为 false 时重启后显示“已中断，等待继续”。从未启动的历史、已完成任务和新补齐轮次均不会自动启动。

可重试故障按冷却策略处理；登录失效、解析规则失效、配置或断点损坏进入等待修复，不因自动恢复配置而无限重启。恢复前重新校验账号与配置兼容性。

请求有超时，数据库事务有执行等待上限；页间休眠和长冷却采用可中断等待，定期检查控制请求。达到优雅停止期限后才强制结束，依靠逐页断点恢复。详情页显示阻塞原因，不能承诺正在进行的网络请求即时结束。

CLI 同时提供拟议的 history、resume、pause、backfill、status 子命令；与网页共享控制路径和单实例约束，不另起一套互相冲突的任务。

只显示实际已覆盖范围，不提供未知全站总量的虚假百分比。运行日志按页滚动展示有限条数，完整日志按既有机制访问。Cookie、代理密码和带凭据 URL 不进入页面、断点、日志或配置预览。

## 10. 账号与代理轮换

- 全量使用 sessions.full_collect 指定账号和网络，不改普通 browse/archive。
- 代理池沿用旧模式：固定入口列表，按 `(当前小时 + 错误偏移) % 入口数量` 选择；时间取应用配置时区。
- 每次请求重新计算；适合重试的请求错误使偏移加一，重试同一页。成功清零连续失败计数，不清零偏移。
- 默认正常页间等待 10～30 秒，换代理重试等待 2 秒。
- 默认连续失败达到代理入口数量后进入整轮冷却；总尝试次数有界，不能与底层重试倍增。
- 数据库/断点错误不换代理。登录失效需处理账号；明确限流尊重服务端等待时间并冷却；页面解析问题不得推进断点。
- 代理入口与真实出口映射由现有代理服务负责，不接入新的代理池 API，不将轮换视为避免风控的保证。
- 无效代理池不能静默直连。

## 11. 配置文件与选项规划

以下为拟议配置契约，实现时按此完成加载、校验、示例文件、配置编辑和迁移兼容。时间和数量均标明单位，枚举不能接受未知值。

### 11.1 新增 config/full_collect.toml

| 字段 | 类型/默认建议 | 说明 |
| --- | --- | --- |
| config_version | 整数，1 | 文件格式版本 |
| base_url | 字符串，用户指定 | 所选站点的无业务筛选列表入口 |
| state_path | 绝对路径，用户指定 | 持久状态 JSON，启动前校验可写 |
| start_mode | date / database / url，默认 date | 首次历史定位方式 |
| start_days_ago | 整数，7 | 未指定固定日期时，初始化冻结当前时间减此天数 |
| start_at | 字符串，空 | 可选带时区 ISO 时间，设置后优先于 start_days_ago |
| start_url | 字符串，空 | url 模式必填，与站点一致 |
| backfill_default_days_ago | 整数，7 | 手动补齐界面的默认新边界；不是定时任务 |
| boundary_overlap_pages | 整数，1 | 到达旧覆盖边界后的有限重叠页数；不能替代边界验证 |
| request_timeout_seconds | 正数，30 | 单次请求超时；实现中明确连接与读取超时含义 |
| page_delay_min_seconds | 非负数，10 | 正常页间最短等待 |
| page_delay_max_seconds | 非负数，30 | 正常页间最长等待 |
| retry_delay_seconds | 非负数，2 | 适合重试的错误后等待 |
| pool_failure_cooldown_seconds | 正数，3600 | 连续失败一轮后的冷却建议值，可调整 |
| resume_after_restart | 布尔，true | 仅恢复被重启打断且未主动暂停的已启动任务 |
| control_poll_seconds | 正数，1 | 可中断等待时检查控制请求的间隔 |
| heartbeat_seconds | 正数，5 | 更新运行状态心跳间隔 |
| stop_grace_seconds | 正数，60 | 调度器等待全量退出的宽限建议值 |
| page_write_timeout_seconds | 正数，30 | 每页数据库写入事务的时间预算，锁等待也应有界 |

首次起点配置只在无历史检查点时生效。修改起点不能悄悄覆盖已有进度；想换范围需显式创建新任务。手动补齐参数在点击时冻结，后续改配置不改变进行中的轮次。

不存在 backfill_interval、自动最新补齐开关或启动补齐计划。模块启用放在 supervisor.toml，避免两个 enabled 开关互相矛盾。

## 13. 验收标准

### 筛选与数据

- 缺少必需标签的 discovered 不会被名称/标签关键词或分组逻辑选入。
- all/any、空列表、精确标签及其他来源兼容性有测试。
- 全量新记录为 filtered_out；旧记录只更新白名单元数据，所有业务字段不变。
- 全量 filtered_out 不因新增 screen 门槛而自动重新排队。

### 首次起点与手动补齐

- 三种起点方式均不默认从最新页开始；一周前的目标跨重启不漂移。
- 数据库无定位记录、边界跨页、同时间多记录和消失锚点均有处理。
- 长时间运行、启动、重启和历史完成都不会自动创建补齐轮次。
- 手动补齐范围预览正确，轮次恢复不变更边界，未完成不提前推进覆盖位置。
- 近期未收录区间明确展示，不因普通 collect 已有部分记录而误报完整。
- 补齐完成后不会自动继续历史。

### 中断、界面与配置

- 请求中、提交前、提交后保存断点前强制终止，恢复不漏页。
- 用户暂停后调度器重启仍暂停；运行任务重启恢复受 resume_after_restart 控制。
- 页间等待/冷却可及时中断，drain 不等待整段历史完成。
- 只有一个工作进程，重复点击与 CLI/Web 同时触发不会覆盖检查点。
- 暂停中、心跳过期、冷却与错误显示真实状态，秘密值不会泄露。
- 新配置文件可打包、安装、编辑和保存；旧配置缺失新字段仍可正常运行。

### 代理与普通流程兼容

- 按小时轮换、出错偏移、成功清零连续失败数及全池冷却均可验证。
- 数据库错误不换代理，HTTP 与池重试不会倍增。
- 全量故障不停止普通 Supervisor 其他任务，普通账号/代理配置保持原行为。

主要使用模拟 HTTP、临时数据库与进程中断测试，不用真实高频访问测试风控。运行 Python/pytest 前执行 conda activate eh。测试文件放 tests/ 且保持 Git 忽略，不强制加入 Git，不绕过忽略规则。

1. 确定必需标签及实际账号/代理配置，落实新配置契约与首次边界定位语义。
2. 实现元数据白名单和 screen 前置门槛，验证普通流程兼容。
3. 实现单页事务、检查点和历史回填，完成中断故障注入。
