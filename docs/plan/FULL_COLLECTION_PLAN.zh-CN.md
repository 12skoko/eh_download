# 全量采集、手动补齐与断点续跑实施计划

日期：2026-09-28；调度与解耦方案更新：2026-09-29

状态：2026-09-30 实施。模块默认关闭，账号、代理池与具体必需标签须按部署实际填写；未启动真实全量采集。

## 1. 已确认的方案

- 复用现有 SpecialWorkflow/SpecialJob 和 Supervisor 特殊任务调度，不建立第二套调度器。
- 整项历史回填是一个 workflow，每轮手动补齐是另一个 workflow；一个 job 执行有限页数。
- 历史首次从一周前开始，可按日期、数据库旧记录或指定分页 URL 定位。
- 补齐必须手动创建；暂停、重启和历史完成不自动创建补齐 workflow。
- 档案复用 manga：新增记录为 filtered_out，remark 添加固定标记；已有记录只更新元数据。
- 每页档案和检查点在同一数据库事务内提交，不再使用独立 JSON 断点文件。
- 特殊任务总并发设为 2，全量模块自身并发设为 1，使用现有公共任务池，不增设全量专用名额。
- 全量使用独立账号和代理池，按小时及适合重试的请求错误轮换代理。
- 提供模块详情页、暂停继续、手动补齐、运行状态和日志。
- screen 增加独立必需标签门槛，为未来无筛选普通增量入口做准备。
- 遵守特殊模块解耦契约：全量业务留在模块内，公共调度不识别全量模块名称、阶段或操作；停止与恢复的能力缺口通过显式通用契约补齐。

不包含全站图片下载、历史并行分片、主动补全所有详情页、历史 filtered_out 自动重新送筛、自动周期补齐、日志轮转或自动清理。

## 3. 数据库变化与档案规则

**不新增数据库表、字段、索引或 status 枚举，不需要 Alembic 结构迁移。** 会增加现有表中的 workflow/job 记录，以及模块定义的 phase 和 payload 内容。

- manga 保存档案。
- SpecialWorkflow 保存任务范围、检查点、累计统计和运行意图。
- SpecialJob 保存执行批次、租约、进度与最早执行时间。
- event_log 沿用任务生命周期和用户操作审计。
- SystemControl 继续控制 Supervisor 和特殊任务整体调度；单个 workflow 暂停使用模块 action，不建立另一份独立状态文件。
- 全量 workflow 无需绑定每个 manga；现有核心支持无档案绑定模块。

新增档案：status=filtered_out，remark 如 `[full_collect] 全量收集建档`，queue_source 使用现有 automatic。写入列表元数据，不应用观察期，不进入 discovered/deferred。

已有档案允许更新：name、real_name、link、torrent_link、posted_at、category、tags_raw、pages、rating、uploader、source_fetched_at。通用 updated_at 可沿用元数据更新时间约定。

禁止更新：status、status_updated_at、remark、queue_source、defer_until、screen_group_id、priority、下载上传字段、人工控制字段、租约、错误和尝试记录等业务状态。不得整体覆盖记录、调用状态转换或因标签变化自动重新送筛。已有全量标记自然保留，其他记录不追加标记。

已有记录不是停止翻页的条件。保留唯一键和有限并发插入冲突重试，不设计复杂的跨采集协调系统。

## 4. screen 必需标签规则

### 4.1 背景与顺序

当前普通 collect 的网址已限定某个标签，screen 因而没有重复检查这个条件。未来普通增量入口改成无标签筛选网址时，必须把该条件显式移入 screen。

新增 `screen_required_tags`，与现有 `collect_tags`、`tag_keywords` 分开：

- collect_tags：构造采集网址。
- tag_keywords：现有筛选中命中后直接选入的关键词。
- screen_required_tags：是否有资格继续参加筛选的前置门槛。

顺序为：读取 EH discovered 候选 → 必需标签检查 → 现有排除、关键词及版本筛选。缺少必需标签时转为 filtered_out，并记录明确的筛选原因；不得被名称关键词或 tag_keywords 的直接选入分支绕过。界面可显示“缺少必需标签”，日志原因可用 required_tag_missing。

标签按 namespace:name 规范化后精确匹配，不能用容易误中的任意子串匹配。处理大小写、首尾空格及当前 tags_raw 的实际存储格式。多标签支持 all/any；单标签两者等价。空列表保持旧行为。

同名分组筛选也要使用相同准入规则：不符合门槛的待筛选候选不能参与版本竞争或反过来淘汰合格候选。已进入下载、已完成等记录仍按现有业务规则处理，不因这次规则上线回退状态。其他来源如 PicACG 不因 EH 标签规则被误伤。

具体必需标签尚未给出，实施前从用户确认的现有采集条件中确定；不能猜测成某个标签，也不能把任意搜索表达式自动转换为精确标签。

### 4.2 与全量 filtered_out 的关系

本期继续保持全量新记录为 filtered_out；新增门槛不代表自动扫描这些历史记录。

该门槛服务于现有 discovered 候选，以及未来无筛选普通增量产生的 discovered。将全量历史档案批量重新送筛属于独立功能，本期不隐式执行。只刷新已有 filtered_out 的元数据也不改变其状态。

## 5. 历史首次起点

### 5.1 三种起点方式

| 模式 | 行为 |
| --- | --- |
| 日期定位（默认） | 初始化时冻结“当前时间减 7 天”的目标时间，使用站点支持并已验证的日期/游标定位方式 |
| 数据库定位 | 查找目标时间附近、不晚于目标时间的 EH 记录，以其数值 GID/链接辅助定位同一站点的列表页 |
| 手工 URL | 用户给定实际可访问的无业务筛选分页 URL；解析和验证后作为首个候选页 |

数据库不存在“一周前的一页”这个历史页面对象。数据库模式只是用记录定位，不能直接把该记录当成一整页已覆盖的证明。没有合适记录时明确报告或由用户选择日期/URL，不静默回退最新页。

日期定位和数据库定位的分页语义必须用真实页面样本验证，不猜测 next 参数包含/排除边界的含义。相同时间多条记录、边界记录删除及站点排序变化都应有测试。

### 5.2 安全边界

- 首次目标时间和解析出的真实页边界持久化，重启不重新计算“今天减 7 天”。
- 允许为了定位读取边界附近页面，但不将目标时间之后的近期记录当作本轮历史范围写入。
- 分页可能跨越目标日期，要逐条应用本轮范围检查，并保留足够的页边界信息，避免漏掉目标时间附近条目。
- URL 需要固定站点、列表模式及无业务筛选范围；账号默认过滤的影响应在初始化检查中提示。
- 普通 collect 的实际覆盖范围不是固定七天，因此“一周前”是减少重叠的起点选择，不作为绝不重叠的证明；已有记录元数据更新规则仍必须可靠。

## 6. 手动补齐轮次

### 6.1 创建与范围

取消旧计划中的每日补齐、到期检查、自动切换与历史完成后的定时补齐。

用户在详情页或 CLI 点击/执行“新建补齐轮次”，先展示范围，再启动：

- 新边界默认定位到本次操作时的一周前，允许用户显式指定日期或分页 URL。
- 旧边界使用最近已覆盖的上边界；第一次使用历史初始化的已落库边界。
- 从新边界向旧边界逐页扫描，并完成有限交界重叠检查。
- 补齐页同样新增 filtered_out、已有仅刷新元数据。
- 本轮完成后更新已覆盖上边界，不自动创建下一轮。

示例：9 月 27 日首次历史回填从约 9 月 20 日开始。11 月 1 日手动补齐，默认新边界约为 10 月 25 日，本轮补齐约 9 月 20 日至 10 月 25 日的区间。10 月 25 日之后的无筛选全量数据仍待用户后续补齐；普通 collect 只覆盖其原筛选范围，不能把这段标成全量完整。

边界仍使用真实分页锚点和经过验证的比较规则，日期仅用于用户选择和显示。不能仅遇到一个已存在 ID 就认定补齐完成。

### 6.2 与历史任务的关系

- 同时只运行一个全量工作进程，不并行跑历史和补齐。
- 创建补齐轮次前，先在页边界暂停历史任务，保存历史位置。
- 补齐完成后进入空闲；由用户点击“继续历史”，不自动切回。
- 尚有未完成补齐轮次时只能继续该轮，不能静默覆盖边界或新建另一轮。
- 补齐中断保留本轮起点、目标旧边界、下一页位置和完成状态。
- 调度器重启可以恢复已经手动创建且处于运行意图的轮次，但这不等于自动创建补齐。
- 历史完成但存在尚未手动补齐区间时，界面分别显示，不能宣称全站已全部完成。


## 7. Workflow 与 Job 的边界

| 对象 | 含义与结束条件 |
| --- | --- |
| full_collect 模块 | 统一配置、详情页、任务列表和控制入口 |
| 历史 workflow | 从冻结起点向历史翻页，到经过验证的网站末页才完成 |
| 补齐 workflow | 从手动选定的新边界扫回旧覆盖边界，完成交界检查后完成 |
| job / 批次 | 抓若干页，到页数或时长预算、暂停、冷却或终点时结束 |
| 页面 | worker 内部循环的一步，也是事务单位，不创建任务 |

每个 job 默认最多 10 页；时长预算仍建议为 600 秒，任一达到后在安全页边界结束。单次请求和事务另设超时，预算不是精确到秒的强杀时间。页数可配置，10 页是本次确认的默认值。

workflow 是数据库记录，不是主动唤醒其他对象的进程。历史 workflow 可以包含一个月内的很多 job，暂停、重启、重试仍沿用同一个 workflow ID。每轮补齐使用新的 workflow ID，不额外引入 task_id。

补齐 payload 保存所属历史 workflow ID 与范围指纹。旧边界只能从同一范围已落库的历史初始边界或已完成的补齐链取得，不能使用未完成轮次推断完整覆盖。历史初始化未成功提交起始页前，不能创建依赖它的补齐。

## 8. 数据库检查点与原子提交

| 位置 | 保存内容 |
| --- | --- |
| workflow.payload | 类型、范围指纹、冻结边界、下一页 URL、累计统计、运行意图、停止原因、独立连续失败计数、代理偏移及下一允许请求时间 |
| workflow.phase | queued、collecting、pausing、paused、cooling、interrupted、waiting_repair、completed 等模块阶段 |
| workflow.progress | 详情页即时摘要，不是唯一恢复依据 |
| job.progress | 本批次页数、数量和执行阶段 |
| job.next_run_at | 下一批次或冷却重试最早领取时间 |
| job 租约 | 令牌、执行者、有效期，防止失效执行者提交 |

现有领取和失败逻辑会重写 workflow.progress，所以可靠检查点必须放 payload，格式由现有 schema_version 管理。暂停用 status=active、phase=paused，完成用 completed；job 沿用现有状态枚举。

每页流程：

1. 事务外请求、解析和校验页面。
2. 开启短事务，按核心锁顺序验证 job 租约，读取最新 workflow 与控制意图。
3. 如果暂停或失去执行资格，放弃本页未提交结果，保留原检查点。
4. 在同一个 Session 中写入本页 manga、下一页游标和累计统计。
5. 一起提交，成功后才记录页面完成并处理下一页。

不能分两个 Session 保存数据和检查点，不能用旧 payload 覆盖刚提交的暂停意图。部分条目解析失败不能静默推进；异常页面不能误判末页。提交结果不确定时重新读取数据库判断位置。

只保留当前页明细和有界内存。取消原计划的 state_path、JSON 断点文件、进程文件锁和双写补偿。数据库备份包含恢复依据，日志清理不影响续跑。

## 9. 调度与并发

### 9.1 谁抓下一页，谁启动下一 job

```text
用户开始历史 / 手动补齐
  → 后台事务创建 workflow + 第一个 queued job
  → Supervisor 领取 job，启动 special worker
  → worker 抓第 1 页、第 2 页……每页提交
  → 达到批次预算且还没完成
  → worker 同一事务完成当前 job、创建延迟 60～120 秒的下一 queued job
  → worker 退出
  → Supervisor 有资格和名额时领取下一 job
```

第 2 页由当前 worker 内部循环发起，不经过调度器。worker 只决定后续工作并入队，不直接启动下一进程。自动续接同一 workflow 的后续 job 不等于自动创建补齐 workflow。

复用 OperationResult.next_operation 与 commit_result；拟议操作名 collect_batch。批次结束 phase 必须允许下一次入队。当前 job 完成与下一 job 创建同事务，避免中途崩溃造成链路丢失。

到真正终点时完成 job 和 workflow，不续接。最后一页已提交但 job 未收尾即崩溃时，恢复需识别终点，只做收尾。

下一 job 仍受全局暂停、drain、维护窗口、特殊任务开关、模块启用、到期时间、并发、资源和阶段校验约束。注册到特殊模块框架，不再注册为普通 MODULES 的 interval/condition 任务。

### 9.2 已确认的并发设置

```toml
# config/supervisor.toml 中已有配置
[special_processing]
enabled = true
max_concurrency = 2
```

```toml
# 拟新增 config/special/full_collect.toml
enabled = true
max_concurrency = 1
```

现有引擎已经支持多进程同时执行。调高总并发本身只需改配置并重启 Supervisor，不需要新增多线程逻辑。全量模块和暂停恢复仍需开发。

总并发 2、全量并发 1 允许全量和其他特殊模块同时运行。其他模块保留各自上限；同一 workflow 始终最多一个 running job。普通 collect 等普通模块不占特殊任务池名额。

这是公共池，不是预留名额：其他任务也可能暂时占满两个名额，让全量等待。每批释放执行资源后重新按现有 next_run_at、job ID 顺序排队，不给全量优先插队或专用槽位。

当前并发值在 Supervisor 初始化缓存，修改后重启生效。本次只写计划，不直接修改部署并发，也不静默覆盖其他部署的自定义设置。

### 9.3 页面等待与 job 间等待

- 每次页面 HTTP 请求结束后，随机生成 5～20 秒的等待间隔，以请求结束时刻为起点；下一次页面请求不得早于该期限。成功和失败请求均纳入节流，解析和数据库处理时间可计入已过去的时间。
- 同一 job 内，worker 使用可中断等待，期间响应暂停/停止，不持有数据库事务或调度锁。此时仍占一个运行 job 名额；它不同于下面的 job 间等待。
- 正常批次续接时，随机生成 60～120 秒间隔，将下一 job 的 next_run_at 设为当前批次数据库收尾时间加该间隔，并与页面请求期限及适用冷却期限取最晚值。不把几种等待机械相加，也不能缩短服务端要求的冷却。
- 当前 worker 入队后立即退出，不在进程里 sleep 60～120 秒，也不为等待启动线程、定时器或新 worker。下一 job 只以 queued 记录留在数据库，不占 running 名额；旧 worker 退出并被回收后，该执行名额可供其他特殊模块使用。
- Supervisor 按现有轮询检查到期 job；到期且有名额时才启动。60～120 秒是随机设定的最早启动延迟，实际启动可能因轮询、暂停或其他任务排队更晚。
- 随机到期时间生成后持久化；轮询、重启或恢复已有 queued job 不重新抽签，也不把尚未到期的等待清零。重复入队调用返回已有 job，不反复修改其期限。
- 最后一页后直接完成 workflow，不创建空 job 等待；用户暂停时也不为了等待而创建下一 job。job 间延迟针对自动批次续接，首次启动可立即排队；人工继续和异常恢复仍须遵守已保存的请求/冷却期限。
- 页面显示“批次间等待”、下一可执行时间和剩余等待；日志记录本次选定间隔、下一 job ID 与到期时间，不逐秒刷日志。

实现复杂度较低：复用 OperationResult.delay_seconds、commit_result 和 SpecialJob.next_run_at 的已有延迟入队机制，增加随机区间配置、期限合并及展示即可；不新增等待线程或调度系统。跨重启保留期限和可中断页内等待纳入测试。

## 10. 暂停、继续和重启恢复

### 10.1 用户控制

详情页提供开始历史、暂停、继续、手动补齐。暂停承担日常停止功能，保留任务和进度，不再添加含义相近的停止按钮。

- queued job：action 在锁内保存暂停意图，撤销待执行 job（可用 cancelled），workflow 保持 active/paused。
- running job：保存暂停意图并显示正在暂停；worker 在请求前、提交前和可中断等待期间检查，收尾当前批次并退出，不续接。
- 继续：清除暂停意图，以原游标创建新的 queued job，不新建 workflow。
- 重复点击：复用 row_version、调度锁与活动 job 唯一性约束，避免重复排队。
- Supervisor 离线：显示不能立即启动或待调度，不能误报正在运行；存活 worker 仍可从数据库读取暂停请求。

使用模块自定义 pause/resume action，不使用通用 workflow cancel。取消是终止，不是暂停。模块通过操作允许阶段、集成校验与结果提交表达暂停；核心仅执行声明的契约，不识别 pausing/paused 等全量阶段，正常暂停不能误报失败。

用户暂停与 worker 页面更新须使用统一锁顺序和最新 payload，不能相互覆盖。只有安全收尾确认后才显示已暂停；心跳过期显示中断/待核实。

历史暂停且执行者停止后才允许创建补齐。在现有调度锁下检查全量 workflow 冲突，暂停历史不能长期占用阻塞补齐的 workflow 级资源。补齐完成后由用户继续历史。

### 10.2 调度器停止与恢复

正常停止/drain 时，Supervisor 经统一停止通知入口告知支持协作停止的执行器；全量执行器在页边界退出，限时等待，不等整个历史 workflow 完成。页间等待可中断，长冷却通过排队而非进程休眠实现。部署和 management 使用同一入口，不自行识别或操作全量 workflow。

resume_after_restart=true 仅恢复已启动、未完成、运行意图仍为继续的任务；用户主动暂停、等待修复、已完成、从未启动的任务不自动执行。设为 false 时，重启前的未完成任务进入 interrupted，等待用户继续，已有 queued 后续 job 也必须被拦截，不能只检查 running job。

现有框架具备租约、心跳和人工 release-expired，但不能据此宣称已有完整自动恢复。新增可选通用生命周期契约，以下为拟议职责，实施前应落实到契约定义和接口测试，不视为现有 API：

| 契约 | 触发入口与职责 |
| --- | --- |
| 协作停止声明与通知 | 模块显式声明支持；Supervisor 在正常停止/drain 时发出通用通知，执行上下文提供可检查的停止原因。框架负责通知与宽限时间，模块决定安全边界和业务收尾；不复用终止性的 workflow cancel 来表示调度器退出 |
| 恢复评估入口 | Supervisor 启动后、首次领取前调用通用恢复服务；后续对新确认的异常退出或遗留任务进行有界检查。仅向已注册并声明恢复能力的模块分发候选，覆盖相关 queued/running 及无活动 job 的未完成 workflow，不另起全量调度器 |
| 模块恢复策略 | 根据最新检查点、用户意图和模块配置返回保持等待、继续、仅收尾或待人工核实的决策；业务阶段及下一操作由模块提供。策略在短事务内执行，不发起 HTTP 请求或启动进程 |
| 框架恢复提交 | 在统一锁和租约协议下重新验证候选与旧执行者资格，原子处理旧 job、资源及后续入队；维护通用审计和幂等约束，不解析全量游标或自行决定业务终点 |

未声明能力的模块沿用现有停止与人工恢复规则，默认不开启自动恢复。模块被禁用、缺失或数据版本不兼容时，不自动续跑。恢复可以维护状态，但实际领取仍受全局暂停、维护、drain、模块开关和并发限制。

启动检查先于受影响任务领取，保证 resume_after_restart=false 不被 queued job 绕过。多 Supervisor 下必须通过既有执行者身份、控制设施及事务锁界定恢复范围；另一 Supervisor 启动不能把仍存活执行者的任务认作遗留任务，也不能反复中断已通过恢复评估的任务。实现前须明确重启归属和幂等依据，不能只用“发现 active workflow”判断；不得以新增全量核心分支或数据库字段替代该契约设计。

全量模块通过上述契约完成以下恢复流程：

1. 检查遗留 running job 和最后成功检查点。
2. 确认旧执行者已停止；或在证明全部全量写入均受租约令牌约束的路径中，先原子撤销旧提交资格。
3. 将旧 job 标为 abandoned，释放 job 资源。
4. 按暂停意图和恢复配置，在同一事务创建续跑 job，或等待用户继续。

不能仅凭租约到期断言旧进程已停止。无法确认或隔离时显示待核实，不重复启动。旧进程失去资格后应停止请求循环，任何未验证租约的写入均禁止。遗留 running 会占现有并发计数，须正确回收，不能跳过计数直接腾位。

全量模块显式声明适用此恢复策略；列表请求虽为读取，本地元数据与检查点写入仍必须受租约保护，不能仅标记为 readonly 就自动判定安全。其他模块不因这次扩展而自动获得相同恢复权限，有下载/上传外部副作用的模块保持原有保守规则。

### 10.3 错误与冷却

可预期的请求错误由全量执行器捕获、分类并记录，先在批次内有限换代理重试。长冷却保存进度、结束当前执行，通过已有结果提交与 next_run_at 排入有界重试，释放进程名额。登录、解析、配置错误进入 waiting_repair。业务错误及重试状态必须保留在模块状态、进度和日志中，worker 正常收尾不代表整项采集成功。

job.attempt_no 是同操作所有历史 job 的递增序号，不能充当连续失败计数。全量在 payload 保存独立计数和上限，成功后按约定清零，避免随着正常批次增长出现指数退避或永久耗尽重试。

代理偏移、下一允许请求时间和冷却截止必要时跨 job 保存，不能靠新 worker 重置状态绕过间隔。

不为全量新增 worker 退出码或 Supervisor 错误分支。已由模块正确处理的请求错误通过正常结果提交结束批次，不能再抛成触发整个特殊任务池冷却的异常；共享数据库等真实系统故障和未预期异常不得被宽泛捕获后伪装成业务冷却，仍遵循已有通用规则。通过异常分类和回归测试验证隔离。

## 12. 独立账号与代理

- sessions.full_collect 指定账号和网络，不改 browse/archive。
- 固定入口池按 `(当前小时 + 错误偏移) % 入口数量` 选择，使用应用配置时区。
- 每次请求重新计算，跨整点切换；适合重试的错误增加偏移，重试同一页。
- 成功清零连续请求失败数，不清零偏移；失败达到池数量后进入整轮冷却。
- 每次页面请求结束后随机等待 5～20 秒，失败换代理也不能绕过该期限；与 retry_delay_seconds、服务端等待期限取最晚可请求时间，避免底层与池重试倍增或等待重复叠加。
- 数据库错误不换代理；明确限流尊重等待时间并冷却；登录异常处理账号，解析失败不推进。
- 入口和真实出口映射由已有代理服务负责，不新增代理池 API，不保证轮换一定免于风控。
- 池无效不得静默直连，代理日志只显示名称或序号。

| integrations/http.py、相关账号网络配置 | 可复用代理选择/请求接口和角色配置；轮换时机、偏移及跨 job 持久化由模块负责 |
| config 加载与校验、web/configuration.py | 新配置及现有字段编辑，不承载工作流状态机 |
| management 配置同步/迁移、有关配置样例 | 新文件部署及兼容；启停走公共入口 |

### 14.3 通用框架能力扩展

| 文件或范围 | 必要改动 |
| --- | --- |
| special/core/contracts.py、execution.py、service.py、repository.py | 按第 10.2 节落实可选协作停止、恢复评估与安全提交契约；正常分批和原子续接复用现有接口，不加入全量阶段或 payload 解释 |
| supervisor/app.py、special/worker.py | 统一生命周期通知与通用恢复服务；worker 沿用原有执行与错误分类 |

上述 Supervisor/worker 改动仅限统一生命周期通知与通用恢复服务调用，不实现全量专用协作停止、恢复或退出码/冷却分支。现有领取排序、并发算法和进程启动方式不因接入全量而重写。通用 Web/CLI 继续按注册信息分发，无明确公共接口缺口时不修改；management 同样不调用全量内部服务。

tests/ 本地测试覆盖模块业务、公共接口、通用生命周期默认兼容及多 Supervisor 竞争恢复，保持 Git 忽略。公共能力扩展与新模块接入分别审查，不能用“保持兼容”代替接口定义或测试。

不增加独立 tasks/full_collect 调度器、普通 MODULES 任务或 checkpoint 文件组件。不改 db/models.py 表结构，不新增 migrations/versions。调总并发无需改引擎，新增全量功能仍需实施代码。

## 15. 验收标准

- 新记录 filtered_out 带标记，已有记录只更新元数据；screen 门槛不可被关键词或分组绕过，其他来源不误伤。
- 起点定位不从最新页默认开始，冻结范围跨 job/重启不漂移；边界跨页、删除锚点和无定位数据有明确处理。
- 历史到有效末页、补齐接上旧范围后才完成 workflow；批次预算结束不误报任务完成。
- 无自动新建补齐；补齐完成不自动继续历史；同一范围已完成边界才可用于下一轮。
- 页数据和检查点同事务，提交前后及终点收尾前强制中断均不漏页。
- 当前 job 完成与后续 job 入队原子，重复点击和竞争领取不会产生重复执行。
- 同一 workflow ID 跨暂停恢复保留，续接用新 job ID；日志不依赖 run_id 每批唯一。
- 总并发 2 时全量和其他特殊模块可并行，全量自身仍为 1；队列尊重暂停、维护和模块开关。
- 用户暂停后重启仍暂停；恢复配置对已 queued/running 均有效；失效执行者不能写入。
- 正常 drain 不等待全部历史，长冷却释放名额，独立失败计数不受 attempt_no 自然增长影响。
- 默认每 job 最多 10 页，页面请求间隔为 5～20 秒；失败换代理不绕过请求等待。
- 下一 job 的随机延迟为 60～120 秒，等待期间无专门 worker/线程且不占 running 名额，其他特殊模块可被领取执行。
- 重启不重新随机或提前领取未到期 job；暂停能中断页内等待，最终完成不创建空的延迟 job；轮询及排队允许实际启动晚于最早到期时间。
- 全量特有错误不扩大为整个特殊池冷却；公共基础设施故障遵守现有规则。
- 状态、进度与日志一致；不误报暂停/启动成功，不暴露秘密；无日志维护功能。
- 新配置可打包、部署、编辑和保存，旧配置兼容；调并发明确需要重启。
- 普通 collect 与其他特殊模块行为回归通过。
- 核心、Supervisor 和通用 worker 不导入 full_collect 模块，不按其名称、阶段或操作分支；接入依靠 catalog 和显式契约，公共业务服务不读取全量检查点。
- 禁用全量后其他模块正常工作；未声明协作停止/自动恢复的模块保持原行为，不自动恢复具有外部副作用的任务。
- 通用生命周期接口使用独立测试执行器验证，不以全量模块作为唯一实现假设；启动恢复先于相关领取，多 Supervisor 不误回收存活任务，重复评估不重复入队或重置等待期限。
- 模块预期请求错误正确落库和延迟，不触发整个特殊池冷却；公共故障及未预期异常不被吞掉，Web/CLI 控制复用注册动作和既有安全校验。

使用模拟 HTTP、临时 PostgreSQL 和进程中断测试；锁、领取和部分唯一索引不能仅用 SQLite 验证。不用真实高频访问测试风控。运行 Python/pytest 前 conda activate eh。测试放 tests/，保持 Git 忽略，不强制加入 Git。

## 16. 实施顺序

1. 确认标签、账号与代理，落实配置契约、边界语义及 workflow payload 格式。
2. 核实公共生命周期能力缺口，明确停止通知、恢复触发、重启归属、幂等与安全提交接口；完成通用扩展及默认兼容测试，不加入全量特判。
3. 实现单页接口、元数据白名单、代理公共能力与 screen 前置门槛，验证普通流程兼容。
4. 在模块目录实现历史回填、逐页事务检查点、有限 job、随机等待、原子续接和手动补齐，经 catalog 注册。
5. 在模块内实现暂停继续、恢复策略及预期网络错误处理，接入通用生命周期契约。
6. 完成注册详情页、配置编辑、日志关联、解耦检查及回归验证。
7. 部署设置总并发 2、全量并发 1，重启 Supervisor 验证，无需数据库 schema 升级。

未确认的预算默认值属于实施建议。实施代码仍需明确授权，并遵守每次授权只允许一次实际写入操作的项目约定。
